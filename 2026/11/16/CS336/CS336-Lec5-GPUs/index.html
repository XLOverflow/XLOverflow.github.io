CS336 Language Modeling: GPUs (Lecture 5)

Created2026-11-15|Updated2026-11-16|Stanford CS336
|Word Count:3.7k|Reading Time:22mins|Post Views:

CS336-Lec5 GPUs

This lecture has one goal: make CUDA and GPUs less of a black box. The sentence I took away is this: computing on a GPU is cheap, and getting the data in front of the compute units is expensive. Every trick below, including FlashAttention at the end, is a way to move less data.

The post has three parts: how a GPU works, what makes it slow and how to make it fast, and finally how these pieces fit together in FlashAttention. The “Where I got stuck” blocks are questions I actually asked while watching the lecture.

How a GPU works

CPUs and GPUs make different trade-offs

Single-core performance stopped improving through Dennard scaling in the 2000s. Since then, compute has grown through parallelism. CPUs and GPUs optimize for different things:

  • A CPU spends its chip area on control logic and cache. Its goal is latency: finish each thread as fast as possible.
  • A GPU spends its area on a large number of tiny compute units (ALUs), with very little support for branching and control. Its goal is throughput: process as much data as possible per unit of time.

Execution model: threads, warps, blocks

A GPU is made of many SMs (Streaming Multiprocessors); an A100 has 108 of them. Three players matter when you write CUDA:

  • Thread: the unit that does the work. All threads run the same instructions on different inputs. This is called SIMT.
  • Warp: threads always execute in groups of 32 consecutively numbered threads. Such a group is a warp, and its threads execute the same instruction at the same time.
  • Block: a group of threads. A block is assigned to one SM and owns a piece of that SM’s shared memory.

Because a warp must execute one instruction at a time, if/else has a cost on a GPU: while the threads on the if branch run, the ones on the else branch wait, and vice versa. This is called control divergence.

Memory hierarchy: closer to the SM is faster

Each thread has its own registers. Threads in the same block share the shared memory inside their SM. Data that crosses blocks has to go through global memory, the memory chips next to the GPU. The access latencies on the slides (in clock cycles) differ a lot:

Memory Location Latency
Shared memory Inside the SM about 20
L1 cache Inside the SM 33
L2 cache On the die, shared by all SMs 200
Global memory Memory chips off the die 290

This table is the starting point for every optimization that follows: read each piece of data from global memory as few times as possible, and reuse it inside the SM.

How SM, CUDA core and Tensor Core relate

Where I got stuck: Are SM, CUDA core and Tensor Core three parallel things? TPUs also have a “Tensor Core”, so why does it map to something completely different?

They are nested. The SM is the container; CUDA cores and Tensor Cores are two kinds of compute units inside it. CUDA cores do general-purpose work (additions, comparisons, elementwise operations). A Tensor Core is a dedicated circuit that only does small matrix multiply-adds.

On the TPU side it is purely a naming collision. Google calls the TPU’s top-level unit a Tensor Core, which plays the role of a GPU’s SM, while the unit that actually multiplies matrices in a TPU is called the MXU. Reading the table below row by row makes it clear:

The real structural difference: a GPU has over a hundred small SMs and is more general. A TPU has only a few large top-level units, bets its area on matrix multiplication, and has no warps. Their matmul performance is similar.

Matrix multiplication gets special treatment

Tensor Cores arrived with the V100 generation. Since then, matrix multiplication has pulled away from other floating-point operations by more than 10x.

At the same time, compute has grown much faster than memory bandwidth. The compute units keep getting faster, but the pipe that feeds them has not kept up.

Takeaway: a GPU is a huge number of workers running the same instructions; matmuls are especially fast; memory lags behind compute, so we have to respect the memory hierarchy.

The bottleneck is memory: roofline and arithmetic intensity

How fast an operation runs depends on how much computation it does per byte of data moved. This ratio is called arithmetic intensity (FLOPs / byte). The roofline model draws it as one picture: at low intensity, throughput grows linearly with intensity and speed is set by memory bandwidth (memory bound). Only when intensity is high enough do you hit the limit of the compute units (compute bound).

ReLU is a typical memory-bound example. For each element it reads once, writes once, and does a single comparison in between. With float32, one read plus one write is 8 bytes for 1 FLOP, so every FLOP moves 8 bytes. There is almost no computation, and all the time goes into moving data.

Where I got stuck: Why does ReLU count as only 1 FLOP?

Because the only computation in max(0, x) is the comparison x < 0. Writing back 0 is a memory access, not an operation. The number does not need to be exact; the point is the order of magnitude. ReLU does about 1 FLOP per element while moving 8 bytes, whereas in a matmul every element you read takes part in N multiply-adds. Note that the slides write bytes / FLOP, the inverse of intensity, where lower is better.

So the second part of the lecture comes down to one question: how do we avoid being memory bound?

Five tricks to make a GPU go fast

1. Low precision

Fewer bits means fewer bytes to move. Switching the ReLU above from float32 to float16 lets the same bandwidth process twice as many elements. Tensor Core matmuls also use mixed precision, with 16-bit inputs and a 32-bit accumulator. Not everything can be lowered, though: sums, softmax and normalization need more precision, and functions with a wide output range such as exp and log need more dynamic range.

The frontier is now 8 bits. An 8-bit float covers a very narrow range, so it comes with a scale factor. Plain FP8 uses one scale for the whole tensor, which crushes small-magnitude elements toward zero. MXFP8 on Blackwell uses one scale per 32 consecutive elements, so blocks do not drag each other down.

MXFP8 has a catch: transposes are no longer free. The blocks are cut along the summation direction of the matmul, and during training the same weight is summed along one direction in the forward pass and along the other in the backward pass (which multiplies by \(W^\top\)). After a transpose, blocks that were quantized row-wise point the wrong way. The only fix is to go back to the high-precision values and quantize again along the other direction, so the same tensor is stored as two quantized copies.

2. Operator fusion

Think of the GPU as a factory and memory as a warehouse. If every step ships its intermediate product back to the warehouse and out again for the next step, all the time is spent on the road. Fusion merges several operations into one kernel, so the data goes in and out once.

For example, computing \(\sin^2 x + \cos^2 x\) naively launches 5 CUDA kernels, and these 5 pointwise operations can be fused into one. Simple fusions like this can be done automatically by a compiler, which is what torch.compile does.

3. Recomputation

Backpropagation needs the intermediate activations from the forward pass, and the usual approach is to store them. But storing and loading are both memory accesses. The slides stack 3 sigmoids: storing the activations costs 8 memory reads and writes across forward and backward, while throwing them away and recomputing them in the backward pass costs only 5. Do a bit more computation to avoid the more expensive memory access. When you are memory bound, that is a good trade.

4. Memory coalescing

Global memory (DRAM) is read in bursts: you ask for one address, and it sends back that whole contiguous section. The threads of a warp issue their reads together, and if the addresses fall within the same burst, the hardware merges them into a single read. That is a coalesced access.

A matrix is stored flattened row by row, so what matters is which locations the threads of a warp read at the same moment. If they read adjacent elements of one row, the addresses are contiguous and can be coalesced. If they read elements in one column across different rows, neighboring addresses are a whole row apart, each thread triggers its own burst, and only one value in each returned section is useful.

Where I got stuck: Does coalesced mean “read only once”?

No. It means everything a burst brings back is useful. Two conditions give the best efficiency: the reads are contiguous, and they start and end on burst boundaries.

5. Tiling (the big one)

In a naive matmul, each thread computes one output \(C_{ij}\) and reads a full row of A and a full column of B from global memory on its own. There are two problems: the same input element is read again and again by many threads, and the column reads of B cannot be coalesced.

Tiling cuts the matrices into \(T \times T\) tiles. One block is responsible for one tile of the output. In each phase it loads one tile of A and one tile of B from global memory into shared memory, the threads of the block read from shared memory and accumulate their partial sums, and then the block moves on to the next pair of tiles.

Where I got stuck: The data still has to be read just as many times, right? How exactly does the number of reads go down?

The total indeed does not change. Each input element is used by N outputs, and nothing can change that. What changes is where it is read from: the naive version does all N reads from global memory, while the tiled version does N/T reads from global memory plus N reads from shared memory.

We only count the global reads because that is where the bottleneck is. Loading a tile also reads contiguous rows, which can be coalesced, so global reads are not just fewer but also more efficient. The way I think of it, tiling is a hand-managed cache: the programmer guarantees that this block of data is in the SM right now, instead of hoping the hardware cache happens to hit.

Three things constrain the tile size: the capacity of shared memory, whether the loads can be coalesced, and whether the tile size divides the matrix dimension.

A mystery: why can a bigger matrix be faster

Karpathy once tweeted that increasing nanoGPT’s vocabulary size from 50257 to 50304 (the nearest multiple of 64) gave about a 25% speedup. The matrix got bigger, so why did it get faster?

Plot the throughput of square matmuls against the side length, and the curve is far from smooth:

There are three phenomena in this plot, and what we have covered explains each one.

The overall rise comes from arithmetic intensity. The larger the matrix, the more computation each loaded element takes part in.

The separate layers come from alignment. Burst boundaries sit at fixed intervals in the one-dimensional address space and know nothing about the shape of the matrix. When the row width is a multiple of the burst size, tile boundaries can line up with burst boundaries. When it is slightly off, every row is shifted by a different amount, no tile placement lines up, and every tile reads some data it does not need. The slides color each point by which number divides the side length, and sizes divisible by larger powers of two land on higher layers.

The periodic sawtooth is called wave quantization. One tile occupies one SM, and an A100 has 108 SMs, so at most 108 tiles run at once. Such a batch is a wave. When the side length goes from 1792 to 1793, the number of tiles jumps from 98 to 120, which is more than 108, and the extra 12 have to wait for a second wave.

The second wave has only 12 SMs working but takes about as long as a full one, so throughput falls off a cliff. As the matrix keeps growing, the second wave fills up and throughput climbs back, until the next overflow. “Quantization” here means that execution time comes in whole waves; it has nothing to do with quantizing numerical precision.

Takeaway: pick dimensions such as hidden size, batch size and vocabulary size as multiples of numbers like 64.

Putting it together: FlashAttention

Attention is two matmuls with a softmax in between: compute \(S = QK^\top\) (an \(N \times N\) score matrix), apply softmax to each row, then multiply by \(V\). A standard implementation writes the whole \(N \times N\) matrix to global memory and reads it back, which is a textbook memory-bound workload.

FlashAttention applies the tiling idea from above: cut Q, K and V into blocks, load them into shared memory, finish the computation inside the SM, and only then write back.

Matmuls can be computed tile by tile. The trouble is the softmax: its denominator needs every score in the row.

The scores inside a tile are complete

Where I got stuck: Isn’t a tile’s result a partial sum? The sum is not finished yet, so how can we start the softmax inside a tile?

This is where I was stuck the longest. The key is that the two matmuls sum over different dimensions. \(S_{ij} = \sum_k Q_{ik} K_{jk}\) sums over the head dimension \(d\), usually only 64 to 128. A tile loads several complete rows of Q and K, so every score in the tile is fully summed in one go and is final. Tiling only cuts the N direction (which queries, which keys), not the d direction.

What is incomplete is something else: the scores of the same query against the other key blocks have not been computed yet, so the row’s max and denominator are incomplete. That part is handled by online softmax.

Online softmax

A numerically stable softmax subtracts the row maximum before exponentiating. The idea of online softmax is that both the max and the denominator can be updated as you scan, and when the max changes you correct what you have accumulated so far.

In attention, replace “one element” with “one tile”, and update the output incrementally as well. For each query, keep three quantities: the largest score so far \(m\), the denominator \(\ell\) relative to \(m\), and the unnormalized output \(O\) (a vector of length \(d\)). For each incoming block of keys and values, once the length-T score vector \(s\) is computed:

\[ \begin{aligned} m_{\text{new}} &= \max(m_{\text{old}},\ \max(s)) \\ \alpha &= e^{\,m_{\text{old}} - m_{\text{new}}} \\ p &= e^{\,s - m_{\text{new}}} \\ \ell_{\text{new}} &= \alpha\,\ell_{\text{old}} + \textstyle\sum p \\ O_{\text{new}} &= \alpha\,O_{\text{old}} + p \cdot V_j \end{aligned} \]

After all blocks are processed, \(O / \ell\) is the output for this query.

The role of \(\alpha\) is to change the reference point. Every term in the old \(\ell\) is \(e^{s - m_{\text{old}}}\), and multiplying by \(e^{m_{\text{old}} - m_{\text{new}}}\) turns it into exactly \(e^{s - m_{\text{new}}}\). When the max does not change, \(\alpha = 1\) and this is a plain running sum. Here is a walk-through with one row of 4 scores split into two tiles:

Where I got stuck: Why maintain \(O\)? Can’t we just keep the unnormalized scores?

Keeping the scores means N numbers per query, and N queries make the full \(N \times N\) matrix, which is exactly what we want to avoid. \(O\) lets us throw the scores away as soon as they are used: after each block, its contribution \(p \cdot V_j\) is added right away. The state per query drops from N numbers to \(d + 2\) numbers, independent of the sequence length. The division can wait until the end because the denominator is the same scalar for the whole row and can be pulled out of the sum.

Three tricks in the forward pass

  • Tiling: scores are computed tile by tile, and only one tile of scores exists at any time.
  • Fusion: the matmul, the exponential, the sum and the multiplication by V all happen in one kernel, so intermediates never touch global memory.
  • Online softmax: this is what lets tiling pass through the softmax.

The backward pass needs \(S\) and the softmax output, which the forward pass did not store, so they are recomputed tile by tile from Q, K and V. That is the recomputation trick from earlier. The paper’s numbers on GPT-2: FLOPs actually go up a little (66.6 vs. 75.2 GFLOPs), but global memory reads and writes drop from 40.3 GB to 4.4 GB, and runtime drops from 41.7 ms to 7.3 ms. More computation, yet nearly 6x faster. That is the best summary of the whole lecture.

This algorithm is not general. It works because attention happens to satisfy two conditions: the summation dimension \(d\) is small enough for a tile to hold complete rows, and everything after the softmax is linear and can be accumulated incrementally.

Key takeaways

  1. GPUs are built for throughput: a huge number of threads run the same instructions, they move in warps of 32, and one block runs on one SM.
  2. Compute has grown faster than memory bandwidth, so most ML workloads are memory bound. Arithmetic intensity is how you tell.
  3. Memory is faster the closer it is to the SM. Every optimization reduces accesses to global memory.
  4. Ways to move less data: low precision (each number is smaller), fusion (fewer round trips), recomputation (trade compute for memory), coalescing (everything you read is useful), tiling (move once, use many times).
  5. Tiling does not reduce the total number of reads. It moves the reads from global memory to shared memory.
  6. Choose matrix dimensions as multiples of numbers like 64. Alignment and wave quantization can both make a slightly bigger matrix faster.
  7. FlashAttention = tiling + fusion + online softmax, plus recomputation in the backward pass. It does more computation and is still faster.

How this connects to the assignment

Assignment 2 (Systems) is basically this lecture done by hand: benchmark with mixed precision, see operator fusion through torch.compile, implement activation checkpointing and recomputation, and finally write a FlashAttention-2 kernel in Triton. When writing the kernel, the five lines of the online softmax update above are the body of the inner loop.
