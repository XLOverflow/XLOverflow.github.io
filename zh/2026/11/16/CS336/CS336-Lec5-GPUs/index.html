CS336 语言建模：GPU（第 5 讲）

发表于2026-11-15|更新于2026-11-16|Stanford CS336
|总字数:4.8k|阅读时长:16分钟|浏览量:

CS336-Lec5 GPUs

这一讲想做的事情只有一件：让 CUDA 和 GPU 不再是黑盒。听完之后我带走了一句话：GPU 上的计算很便宜，把数据搬到计算单元面前很贵。后面所有的技巧，包括最后的 FlashAttention，都是在想办法少搬数据。

全文分三部分：GPU 是怎么工作的，什么让它变慢、怎么让它变快，最后把这些拼起来看 FlashAttention。文中有几处「我卡住的地方」，是我看视频时真实问过的问题。

GPU 是怎么工作的

CPU 和 GPU 的取舍不同

单核性能靠 Dennard scaling 提升的时代在 2000 年代就结束了，之后算力的增长靠的是并行。CPU 和 GPU 是两种不同的优化目标：

  • CPU 把芯片面积花在控制逻辑和 cache 上，目标是 latency，让每个线程尽快跑完。
  • GPU 把面积花在大量很小的运算单元（ALU）上，分支和控制能力很弱，目标是 throughput，单位时间处理尽可能多的数据。

执行模型：thread、warp、block

GPU 由很多个 SM（Streaming Multiprocessor）组成，A100 上有 108 个。写 CUDA 程序时要记住三个角色：

  • Thread：真正干活的单位。所有 thread 执行同一段指令，只是输入不同，这叫 SIMT。
  • Warp：thread 永远以 32 个连续编号为一组一起执行，这一组叫一个 warp。同一个 warp 里的 thread 在同一拍执行同一条指令。
  • Block：一组 thread。一个 block 被分配到一个 SM 上运行，拥有这个 SM 上的一块 shared memory。

因为一个 warp 必须执行同一条指令，if/else 在 GPU 上是有代价的：走 if 分支的 thread 执行时，走 else 的那些只能空等，反过来也一样。这叫 control divergence。

内存层级：离 SM 越近越快

每个 thread 有自己的寄存器，同一个 block 的 thread 共享 SM 内部的 shared memory，跨 block 的数据只能走 global memory，也就是芯片旁边的显存。slides 给的访问延迟（单位是时钟周期）差距很大：

内存 位置 延迟
Shared memory SM 内部 约 20
L1 cache SM 内部 33
L2 cache 芯片上，所有 SM 共享 200
Global memory 芯片外的显存 290

这张表是后面所有优化的出发点：同一份数据，尽量只从 global memory 读一次，之后都在 SM 内部用。

SM、CUDA core、Tensor Core 到底是什么关系

我卡住的地方：SM、CUDA core、Tensor Core 是并列的三种东西吗？TPU 里也有 Tensor Core，为什么对应的东西完全不一样？

它们是包含关系。SM 是容器，CUDA core 和 Tensor Core 是 SM 里的两种运算单元：CUDA core 做通用运算（加法、比较、逐元素操作），Tensor Core 是一块只做小矩阵乘加的专用电路。

TPU 那边纯粹是撞了名字。Google 把 TPU 的顶层单元叫 Tensor Core，它的地位相当于 GPU 的 SM，而 TPU 里真正做矩阵乘的单元叫 MXU。按行对照下面这张表就清楚了：

结构上的真实差别是：GPU 有上百个小的 SM，更通用；TPU 只有很少几个大的顶层单元，把面积押在矩阵乘上，没有 warp 这一层。两者的矩阵乘性能相近。

矩阵乘是被特殊照顾的

从 V100 这一代开始有了 Tensor Core，之后矩阵乘的速度就和其他浮点运算拉开了，差距超过 10 倍。

同时，算力的增长速度远快于内存带宽的增长速度。计算单元越来越快，喂数据的管道却没跟上。

小结：GPU 是大量执行相同指令的 worker；矩阵乘特别快；内存跟不上计算，所以要尊重内存层级。

瓶颈在内存：roofline 和 arithmetic intensity

一个操作有多快，取决于它每搬一个字节的数据能做多少计算，这个比值叫 arithmetic intensity（FLOPs / byte）。roofline 模型把它画成一张图：intensity 低的时候，吞吐量随它线性增长，速度由内存带宽决定（memory bound）；intensity 高到一定程度，才会顶到计算单元的上限（compute bound）。

ReLU 是一个典型的 memory bound 例子。对每个元素，它要读一次、写一次，中间只做一次比较。用 float32 时一读一写共 8 个字节，对应 1 个 FLOP，也就是每个 FLOP 要搬 8 个字节。计算几乎为零，时间都花在搬数据上。

我卡住的地方：为什么 ReLU 只算 1 个 FLOP？

因为 max(0, x) 唯一的计算就是一次比较 x < 0，写回 0 属于内存访问，不算运算。这个数不必抠得很精确，重点是量级：ReLU 每个元素约 1 个 FLOP 却要搬 8 个字节，而矩阵乘里每读进来一个元素会参与 N 次乘加。注意 slides 上写的 bytes / FLOP 是 intensity 的倒数，越低越好。

所以这一讲第二部分的问题可以归结为一句话：怎样避免 memory bound？

让 GPU 跑快的五个技巧

1. 低精度

位数越少，要搬的字节越少。上面的 ReLU 从 float32 换成 float16，同样的带宽能处理两倍的元素。Tensor Core 的矩阵乘也是用 16 位输入、32 位累加的混合精度来做的。不过不是所有操作都能降精度：求和、softmax、归一化需要更高的精度，exp、log 这类输出范围很大的函数需要更大的数值范围。

前沿已经到了 8 位。8 位浮点能表示的范围很窄，所以要配一个缩放因子（scale）。普通 FP8 是整个 tensor 共用一个 scale，量级小的元素会被压到接近 0。Blackwell 上的 MXFP8 改成每 32 个连续元素一个 scale，各块互不拖累。

MXFP8 带来一个麻烦：转置不再是免费的。块是沿着矩阵乘的求和方向切的，而训练时同一个权重在 forward 里沿一个方向求和，在 backward 里（乘的是 \(W^\top\)）沿另一个方向求和。按行切块量化出来的结果，转置之后块的方向就不对了，只能回到高精度原值按另一个方向重新量化一遍，于是同一个 tensor 要存两份量化版本。

2. Operator fusion

把 GPU 想成工厂，把内存想成仓库。如果每做一步操作都要把半成品运回仓库，再运出来做下一步，时间就都花在路上了。Fusion 是把多步操作合并成一个 kernel，数据只进出一次。

比如直接计算 \(\sin^2 x + \cos^2 x\) 会启动 5 个 CUDA kernel，而这 5 个逐元素操作可以合成一个。这类简单的 fusion 编译器能自动完成，torch.compile 做的就是这件事。

3. Recomputation

反向传播需要前向的中间激活值，通常的做法是存下来。但存和取都是内存访问。slides 的例子是叠 3 个 sigmoid：存激活值的做法前向加反向一共 8 次内存读写；把激活值扔掉、反向时重新算一遍，只需要 5 次。多做一点计算，换掉更贵的内存访问，在 memory bound 的时候是划算的。

4. Memory coalescing

Global memory（DRAM）是按 burst 读的：你要 1 个地址的数据，它会把那一整段连续的数据一起送回来。一个 warp 的 thread 是同时发出读取的，如果它们要的地址落在同一个 burst 里，硬件就把这些读取合并成一次，这叫 coalesced。

矩阵在内存里是按行拍平存储的，所以要看的是同一时刻一个 warp 的各个 thread 读的是哪些位置。如果它们读的是同一行里相邻的元素，地址连续，可以合并。如果它们读的是同一列上不同行的元素，相邻两个地址隔了一整行，每个 thread 各触发一次 burst，每次带回来的一整段里只有一个数有用。

我卡住的地方：coalesced 是不是「只读一次」的意思？

不是。它的意思是每次 burst 带回来的数据全都有用。效率最高的条件有两条：连续，并且起止位置对齐 burst 的边界。

5. Tiling（最重要的一个）

朴素的矩阵乘里，每个 thread 负责一个输出 \(C_{ij}\)，各自去 global memory 读 A 的一整行和 B 的一整列。问题有两个：同一个输入元素被很多 thread 重复读取，而且读 B 的那一列是无法 coalesce 的。

Tiling 的做法是把矩阵切成 \(T \times T\) 的小块（tile）。一个 block 负责输出的一个 tile，每一轮把 A 的一个 tile 和 B 的一个 tile 从 global memory 载入 shared memory，block 里的 thread 都从 shared memory 取数，各自累加部分和，然后换下一对 tile。

我卡住的地方：数据不还是要读那么多次吗？读取次数到底是怎么减少的？

总次数确实没有变。每个输入元素会被 N 个输出用到，这一点改变不了。变的是从哪里读：朴素做法 N 次全是 global memory，tiling 之后是 N/T 次 global 加上 N 次 shared。

只数 global 的次数，是因为瓶颈在那里。另外载入 tile 时是按行连续读的，可以 coalesce，所以 global 读取不光次数少了，每次的效率也更高。我的理解是，tiling 就是一块手动管理的 cache：程序员明确保证这块数据现在就在 SM 里，而不是指望硬件的 cache 碰巧命中。

Tile 的大小受三件事约束：shared memory 的容量、能不能 coalesce、以及矩阵的边长能不能被 tile 整除。

一个谜题：为什么矩阵大一点反而更快

Karpathy 发过一条推：把 nanoGPT 的词表从 50257 调大到 50304（最近的 64 的倍数），速度提升了约 25%。矩阵变大了，为什么反而更快？

这张图上有三种现象，前面的知识正好能解释：

整体上升来自 arithmetic intensity。矩阵越大，每个读进来的元素参与的计算越多。

分成几层来自对齐。Burst 的边界是按固定间隔划在一维地址上的，和矩阵形状无关。行宽是 burst 的整数倍时，tile 的边界可以和 burst 的边界重合；行宽差一点，每一行的错位量都不同，怎么摆 tile 都对不齐，每个 tile 都要多读一些用不上的数据。slides 的图按边长能被哪个数整除给点上了色，能被越大的 2 的幂整除的边长，落在越靠上的那一层。

周期性的锯齿叫 wave quantization。一个 tile 占一个 SM，A100 有 108 个 SM，所以一批最多同时跑 108 个 tile，这一批叫一个 wave。边长从 1792 变到 1793 时，tile 数从 98 跳到 120，超过了 108，多出来的 12 个必须等第二个 wave。

第二个 wave 只有 12 个 SM 在工作，花的时间却和满的 wave 差不多，所以吞吐量断崖式下跌。矩阵继续变大，第二个 wave 被逐渐填满，吞吐量又爬回来，直到下一次溢出。这里的 quantization 指的是执行时间只能是整数个 wave，和数值精度的量化不是一回事。

小结：hidden size、batch size、词表大小这类维度，尽量选 64 这类数的倍数。

拼起来：FlashAttention

Attention 是两个矩阵乘中间夹一个 softmax：先算 \(S = QK^\top\)（\(N \times N\) 的 score 矩阵），对每一行做 softmax，再乘 \(V\)。常规实现要把整个 \(N \times N\) 的矩阵写进 global memory 再读回来，是典型的 memory bound。

FlashAttention 的思路就是前面的 tiling：把 Q、K、V 切成块载入 shared memory，在 SM 内部算完再写回去。

矩阵乘可以一块一块算，麻烦在 softmax：它的分母需要一整行所有的 score。

每个 tile 里的 score 是完整的

我卡住的地方：tile 算出来的不是部分和吗？sum 都还没加全，怎么能在 tile 里就开始做 softmax？

这是我卡得最久的地方。关键在于两个矩阵乘的求和维度不同。\(S_{ij} = \sum_k Q_{ik} K_{jk}\) 的求和维度是 head dimension \(d\)，通常只有 64 到 128，一个 tile 载入的是若干行完整的 Q 和 K，所以 tile 里的每个 score 一次就加完了，是最终值。Tiling 只切了 N 方向（哪些 query、哪些 key），没有切 d 方向。

不完整的是另一件事：同一个 query 对其他 key 块的 score 还没算出来，所以这一行的 max 和分母不全。这部分交给 online softmax。

Online softmax

数值稳定的 softmax 会先减去这一行的最大值再取指数。Online softmax 的想法是：max 和分母都可以边扫边更新，max 变了就把之前的累加结果修正一下。

放到 attention 里，把「一个元素」换成「一个 tile」，并且让输出也跟着增量更新。对每个 query，维护三个量：到目前为止的最大 score \(m\)，以 \(m\) 为基准的分母 \(\ell\)，以及未归一化的输出 \(O\)（长度为 \(d\) 的向量）。每来一块 key 和 value，长度为 T 的 score 向量 \(s\) 算出来之后：

\[ \begin{aligned} m_{\text{new}} &= \max(m_{\text{old}},\ \max(s)) \\ \alpha &= e^{\,m_{\text{old}} - m_{\text{new}}} \\ p &= e^{\,s - m_{\text{new}}} \\ \ell_{\text{new}} &= \alpha\,\ell_{\text{old}} + \textstyle\sum p \\ O_{\text{new}} &= \alpha\,O_{\text{old}} + p \cdot V_j \end{aligned} \]

所有块处理完之后，\(O / \ell\) 就是这个 query 的输出。

\(\alpha\) 的作用是换基准。旧的 \(\ell\) 里每一项是 \(e^{s - m_{\text{old}}}\)，乘上 \(e^{m_{\text{old}} - m_{\text{new}}}\) 之后正好变成 \(e^{s - m_{\text{new}}}\)。max 没变的时候 \(\alpha = 1\)，就是普通的累加。用一行 4 个 score、分成两个 tile 的例子走一遍：

我卡住的地方：为什么要维护 \(O\)，把未归一化的 score 存着不行吗？

存 score 的话，每个 query 要存 N 个数，N 个 query 就是完整的 \(N \times N\) 矩阵，这正是要避免的。\(O\) 的作用是让 score 用完即丢：每处理一块，立刻把这块的贡献 \(p \cdot V_j\) 加进去。于是每个 query 的状态从 N 个数降到 \(d + 2\) 个数，和序列长度无关。除法可以留到最后，是因为分母对一整行是同一个标量，可以提到求和外面。

前向过程里的三个技巧

  • Tiling：score 是一块一块算的，任何时刻只有一个 tile 的 score 存在。
  • Fusion：矩阵乘、取指数、求和、乘 V 都在同一个 kernel 里完成，中间结果不落 global memory。
  • Online softmax：让 tiling 能穿过 softmax。

反向传播需要 \(S\) 和 softmax 的结果，而前向没有存它们，所以反向时从 Q、K、V 按 tile 重新算一遍，这正是前面的 recomputation。论文里 GPT-2 上的数据是：FLOPs 反而多了一些（66.6 对 75.2 GFLOPs），但 global memory 的读写从 40.3 GB 降到 4.4 GB，运行时间从 41.7 ms 降到 7.3 ms。计算变多了，速度却快了近 6 倍，这是整节课最好的注脚。

这个算法并不通用。它成立是因为 attention 恰好满足两个条件：求和维度 \(d\) 小到一个 tile 能装下完整的行，以及 softmax 之后的部分是线性的、可以增量累加。

要点回顾

  1. GPU 为 throughput 而设计：大量 thread 执行相同的指令，32 个一组的 warp 一起走，一个 block 跑在一个 SM 上。
  2. 算力增长比内存带宽快，所以多数 ML 负载是 memory bound。判断标准是 arithmetic intensity。
  3. 内存离 SM 越近越快。所有优化都在减少对 global memory 的访问。
  4. 少搬数据的办法：低精度（每个数更小）、fusion（少往返）、recomputation（用计算换内存）、coalescing（每次读回来的都有用）、tiling（搬一次、用多次）。
  5. Tiling 不减少读取的总次数，它把读取从 global memory 换到了 shared memory。
  6. 矩阵维度尽量取 64 这类数的倍数。对齐和 wave quantization 都会让「大一点」的矩阵反而更快。
  7. FlashAttention = tiling + fusion + online softmax，反向再加 recomputation。它的计算量更大，但更快。

和作业的关系

Assignment 2（Systems）基本就是把这一讲动手做一遍：用 mixed precision 做 benchmark，用 torch.compile 体会 operator fusion，做 activation checkpointing 和 recomputation，最后用 Triton 写一个 FlashAttention-2 的 kernel。写 kernel 的时候，上面 online softmax 的那五行公式就是内层循环的主体。
